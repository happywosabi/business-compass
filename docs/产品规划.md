# 商业罗盘 — 产品规划

> 状态：实体小店与在产果园首版已实现，后续规划见开发计划
> 最后更新：2026-11-04

---

## 一、产品定位

帮助**个人创业者和小店主**判断一个商业模式是否可行、如何优化，并持续辅助其获客与运营。面向国内用户。

核心闭环（"罗盘"的含义）：

```
评估商业模式 → 找出最关键的假设 → 设计实验验证 / 发内容获客
      ↑                                              ↓
   重新评估  ←──────────  填回真实数据、对比偏差  ←──────
```

目标是让用户每周都有理由回来，而不是用一次就走。

---

## 二、目标用户带来的设计原则

用户大多不懂财务术语、主要用手机、关心的是"这家店能不能赚钱、多久回本"。

- **说大白话**：不问"获客成本、LTV"，而是问"房租多少、一天大概多少客人、一份卖多少钱、请几个员工"。专业指标由计算引擎在内部换算
- **"不知道"也能继续**：用户答不上来的参数，用行业默认值代替，并在档案里标注为"待验证的假设"
- **手机优先**：所有页面先按手机屏幕设计
- **结论要具体**：例如"按现在的假设，第 14 个月回本；如果客流比预期少 20%，就回不了本"，而不是抽象的评分
- **模板优先级**：
  1. 实体小店（餐饮、零售、美业、本地服务）——共用一套门店模型
  2. 网店 / 电商
  3. 个人服务 / 知识付费
- **内容平台**：朋友圈、小红书、抖音、大众点评、视频号
- **热点来源**：对小店主来说，节日节气营销日历、本地热点、行业热点比全国热搜更有用
- **政策雷达重点**：个体工商户和小微企业补贴、创业担保贷款、小规模纳税人税收优惠，按城市匹配

## 三、核心概念：商业档案

**每个用户可以有多个商业档案，每个档案对应一个商业模式。** 所有功能都围绕档案读写。

> 详细数据结构见 [商业档案数据结构](商业档案数据结构.md)

### 3.1 档案内容

| 模块 | 内容 |
|---|---|
| 基本信息 | 名称、行业、所在城市、阶段（想法 / 筹备 / 已运营） |
| 商业模式类型 | 实体小店 / 网店 / 个人服务 … 决定使用哪套评估模板 |
| 价值主张 | 目标客户、解决的问题、差异化、渠道 |
| 关键假设 | 每个参数都存「悲观 / 中性 / 乐观」三个值，并标注来源（用户填写 / AI 推断 / 行业默认值） |
| 财务参数 | 售价、成本、客流、房租、人工、装修、启动资金等 |
| 品牌语气 | 用户提供的历史文案、提取出的写作风格（供内容生成使用） |
| 真实数据 | 按时间记录的实际经营数据（周/月） |
| 验证实验 | 每个实验的假设、方法、结果、结论 |
| 产出物 | 评估报告、财务预测、商业计划书等 |

### 3.2 版本历史

每次评估生成一份**快照**，记录当时的参数和结论。用户可以对比"三个月前的判断"和"现在的判断"，看到假设如何被验证或推翻。

### 3.3 各功能与档案的关系

| 功能 | 读取 | 写入 |
|---|---|---|
| 商业模式评估 | 全部 | 关键假设、财务参数、评估快照 |
| 热点内容生成 | 行业、城市、目标客户、品牌语气 | 生成的内容记录 |
| 财务预测 | 财务参数、关键假设 | 预测结果 |
| 假设验证计划 | 关键假设、敏感性分析结果 | 验证实验 |
| 填回真实数据 | 关键假设 | 真实数据、偏差提醒 |
| 生成商业计划书 | 全部 | 商业计划书 |
| 政策雷达 | 行业、城市、阶段 | 匹配到的政策 |
| 案例库 | 商业模式类型、行业 | — |

## 四、核心功能

### 4.1 商业模式评估

**原则：AI 负责对话和解释，数学计算交给代码。**

> 实体小店的完整测算模型见 [实体小店测算模型](实体小店测算模型.md)
> AI 访谈流程见 [AI 访谈流程](AI访谈流程.md)

- **表单 + 对话结合**：对话的本质是填表。页面上显示结构化字段，AI 从对话中提取参数实时填入，缺什么追问什么（function calling 实现）
- **按商业模式类型分模板**：

  | 类型 | 关键指标 |
  |---|---|
  | 餐饮门店 | 客流、客单价、翻台率、坪效、租金占比、食材成本占比 |
  | 零售门店 | 客流、进店转化率、客单价、毛利率、库存周转 |
  | 美业 / 本地服务 | 复购率、会员储值、人效 |
  | 网店 / 电商 | 转化率、客单价、退货率、平台扣点、推广费占比 |
  | 个人服务 / 知识付费 | 获客渠道、转化率、复购率、时间投入 |

- **数学模型四层**
  1. 单位经济：每单 / 每位客人赚多少、拉一个新客人的成本、回本周期
  2. 财务预测：现金流、盈亏平衡点、启动资金、现金能撑多久
  3. 不确定性：敏感性分析（找出影响最大的变量）；后续加蒙特卡洛模拟（盈利概率）
  4. 定性评分：市场、竞争、选址/渠道、个人能力；AI 打分须附理由，权重公开
- **输出**：给出「最致命的 3 个假设 + 最敏感的变量 + 低成本验证方法」，用大白话
- **行业基准校验**：用户输入明显偏离行业水平时主动提醒（用户普遍过度乐观）
- **行业基准数据来源**：公开行业报告整理 + AI 估算（标注为低可信度）。这部分是内容工作，需要持续积累
- **Skill 配置化**：每个 skill = 输入字段定义 + 系统提示词 + 可调用工具 + 输出模板，存 YAML / 数据库，新增分析框架无需改代码

### 4.2 热点追踪与内容生成

- **数据源**：
  - 节日节气营销日历（可提前规划，最稳定）
  - 全国热榜：热榜聚合服务（如 DailyHotApi，可 Docker 自部署）
  - 本地 / 行业热点：已接中新网及食品伙伴网的固定 RSS，后续可接付费搜索 API
  - 不自行硬爬各平台；当前默认仅使用公开 RSS 摘要，不宣称平台热搜排名
- **频率**：每 1–2 小时采集；每天早上推送"今日可用选题"
- **处理流程**：采集 → 去重合并（向量聚类） → 安全过滤（灾难、事故、敏感事件不蹭） → 趋势判断（上升中的优先） → 与商业档案匹配打分
- **两步生成**：先选切入点，下方可选关联热点，生成前检索热点背景再按需生成全文
- **分平台写作 skill**：朋友圈、小红书、抖音口播稿、大众点评、视频号
- **品牌语气**：从用户历史文案提取风格
- **事实性**：只基于抓取到的原文写作，标注来源
- **边界**：不做自动发布、不做批量评论，定位为"给用户自己的账号写原创内容"
- **DeepSeek 使用**：系统提示词和档案等固定内容放在提示词最前面以命中上下文缓存；简单分类打分用对话模型，深度分析用推理模型

## 五、扩展功能（已确认）

### 5.1 财务预测
- 生成 12 / 24 / 36 个月的月度利润表和现金流预测
- 输出盈亏平衡点、所需启动资金、现金能撑多久
- 支持悲观 / 中性 / 乐观三种情景对比
- 支持导出 Excel

### 5.2 假设验证计划
- 根据敏感性分析，找出"如果错了就会失败"的关键假设
- 为每个假设设计低成本实验，例如：蹲点数客流、摆摊试卖、预售、社群问卷
- 记录实验结果，验证通过或推翻后自动更新档案中的假设

### 5.3 填回真实数据 + 偏差提醒
- 用户按周 / 月填写实际经营数据（尽量简单：营业额、客数、主要支出）
- 与模型假设对比，偏差过大时提醒，例如"实际客流比假设少 30%"
- 偏差触发重新评估，形成闭环

### 5.4 生成商业计划书
- 基于档案和评估结果生成商业计划书 / 一页纸摘要（可用于申请创业贷款、找合伙人）
- 数据全部来自档案和计算引擎，AI 只负责组织和表述
- 支持导出（PDF / Word，格式待定）

### 5.5 政策雷达
- 采集各级政府的创业补贴、创业担保贷款、税收优惠等政策
- 按档案的行业、城市、阶段匹配推送
- 与热点采集复用同一套采集 → 处理 → 匹配流程

### 5.6 案例库
- 收录同类商业模式的成功和失败案例
- 评估时按商业模式类型和行业检索相关案例作为参考（RAG）
- 失败案例同样重要：帮助用户识别常见的失败原因

## 七、技术架构

### 7.1 原则（一个人开发）

- **组件越少越好**：每多一个服务，就多一份运维和排错成本
- **选主流、文档多的技术**：遇到问题容易搜到答案，AI 编程助手也更熟悉
- **一个代码库、一个后端镜像**：API 和定时任务用同一个镜像，只是启动命令不同
- **计算引擎必须有单元测试**：用手算过的例子核对公式，数字算错会让整个产品失去信任
- **先跑通一个完整闭环，再扩展功能**

### 7.2 部署结构（Docker Compose）

```
用户 ──HTTPS──▶ Nginx
                  ├─ 前端静态文件（打包后由 Nginx 直接托管）
                  └─▶ api       FastAPI
                                 ├─ 评估引擎（纯计算，不用 AI）
                                 ├─ AI 编排层（skill 配置 + 工具调用）
                                 └─ LLM 调用层（DeepSeek：计量 / 限额 / 重试 / 日志）

  worker     与 api 同一个镜像，运行定时任务（热点 / 政策采集、去重合并、生成选题）
  postgres   业务数据 + pgvector 向量
  hotapi     热榜聚合服务
```

共 4 个服务。暂不引入 Redis 和任务队列，需要时再加。

### 7.3 技术选型

| 部分 | 选型 | 说明 |
|---|---|---|
| 后端 | Python + FastAPI | 模块化单体，按功能分模块 |
| 数据库 | PostgreSQL + pgvector | 业务数据和向量放在同一个库 |
| 数据库访问 | SQLAlchemy + Alembic | Alembic 管理表结构变更 |
| 数据校验 | Pydantic | FastAPI 自带 |
| 计算 | Python 自带功能 + Pydantic | 第一版计算量很小，不需要 numpy；做蒙特卡洛模拟时再引入 |
| 依赖管理 | uv | 管理 Python 版本和依赖 |
| 大模型调用 | OpenAI 官方 Python SDK，指向 DeepSeek 地址 | DeepSeek 兼容 OpenAI 接口，以后换模型只改配置 |
| 向量（embedding） | 阿里云百炼 qwen3.7-text-embedding-flash | 用于热点去重合并、案例库检索。已验证：输出 **1024 维**。向量维度建表时固定，表中记录所用模型，换模型需重算全部向量 |
| 定时任务 | APScheduler | 跑在 worker 容器里 |
| 限流 | Nginx limit_req | 利用现有运维经验，不用写代码 |
| 登录 | 邮箱注册 + 密码登录 | 注册需验证邮箱；密码用 Argon2id 哈希；详见[商业档案数据结构](商业档案数据结构.md)第四节 |
| 前端 | 待定（建议 Vue 3 + 手机端组件库 Vant） | 中文资料多，手机端组件现成 |
| 反向代理 | Nginx | HTTPS、静态文件、限流 |

### 7.4 运维要点

- PostgreSQL 每日自动备份，并复制到另一台机器或对象存储
- 密钥（DeepSeek、阿里云百炼、邮件服务）放在 `.env`，不提交到代码仓库
- 只有 Nginx 对外暴露端口，其余服务走 Docker 内部网络
- 容器以非 root 用户运行
- 每个用户每天的 AI 调用设上限
- 安全重点：所有档案查询强制校验"属于当前用户"（防越权）

新增供应商自身经营档案，首期聚焦已投产果园，多品种、批发零售并存，财务分析与获客内容并重。核算经营期总账，区别经营结余与扣未付酬家庭劳动后的收益。暂不支持幼树期、多年建园回本、逐月回款和资金周转。采购商/消费者内容显式切换，缺失事实留待填，内部财务不参与获客文案。

实体小店内新增“水果店（零售）”，支持筹备与经营中整店前瞻；与果农供应商档案独立。营业额日/月原始值、两种互斥采购成本口径、成本加权损耗、库存占用、老板报酬及公开商品资料构成首版范围。完整边界见[水果零售店测算模型](水果零售店测算模型.md)。不扩展为商品库存系统或历史经营台账。
