# 商业档案数据结构

> 状态：已确认
> 最后更新：2026-11-04
> 相关文档：[产品规划](产品规划.md)、[实体小店测算模型](实体小店测算模型.md)

---

## 一、设计要点

1. **普通字段 + JSON 字段混合**：经常用来筛选的信息（所属用户、城市、业态、阶段）用普通字段；测算参数用 JSON 字段（PostgreSQL 的 jsonb），由代码里的 Pydantic 模型校验。以后新增"网店""个人服务"模板时不用改表结构
2. **工作稿 + 不可修改的快照**：档案里只有一份"当前参数"可以修改；每次评估时，把参数和计算结果完整复制成一份快照，此后不再修改。这样才能对比"三个月前的判断"和"现在的判断"
3. **三档用"悲观 / 中性 / 乐观"，不用"低 / 中 / 高"**：成本类参数的悲观值是高值，用"低 / 高"容易弄反
4. **只存原始输入，不存推导值**：押金金额、装修期房租、比例费率 f 等都由计算引擎现算，避免数据前后不一致
5. **每次参数修改都留记录**：谁改的、为什么改（用户修改 / AI 提取 / 实验结果 / 真实数据），既能讲清"假设是如何被验证或推翻的"，也能排查 AI 提取错误
6. **所有档案数据都通过同一个入口访问**：从根本上防止越权（见第十二节）

## 二、约定

| 项目 | 约定 |
|---|---|
| 主键 | 全部使用 UUID（随机、不可猜） |
| 时间 | 存 UTC（timestamptz），显示时转为北京时间 |
| 金额 | 单位为元。测算参数存在 JSON 中为普通数字；真实经营数据用 numeric(12,2) |
| 比例 | 一律存小数：8% 存为 0.08 |
| 时长 | 测算中一律以"月"为单位 |
| 命名 | 表名、字段名用英文小写加下划线；界面上显示的中文名放在模板配置里 |
| 通用字段 | 每张表都有 `created_at`；可修改的表另有 `updated_at` |
| 删除 | 用户数据先软删除（`deleted_at`），30 天后由定时任务彻底删除 |

字段类型说明：`uuid` 唯一编号、`text` 文本、`int` 整数、`numeric` 精确小数、`date` 日期、`timestamptz` 日期时间、`jsonb` JSON 数据。

## 三、表关系总览

```
users ─┬─< sessions
       ├─< email_tokens
       ├─< llm_usage
       ├─< notifications                      （后续）
       └─< profiles ─┬─< parameter_changes
                     ├─< evaluations ─< documents   （documents 后续）
                     ├─< conversations ─< messages
                     ├─< topic_suggestions ─< posts
                     ├─< experiments                 （后续）
                     └─< actual_records              （后续）
```

`─<` 表示"一对多"，例如一个用户有多个档案。

| 表 | 用途 | 版本 |
|---|---|---|
| users | 用户 | 第一版 |
| sessions | 登录会话 | 第一版 |
| email_tokens | 验证邮箱、重置密码的一次性令牌 | 第一版 |
| llm_usage | 大模型调用计量（每日限额） | 第一版 |
| profiles | 商业档案 | 第一版 |
| parameter_changes | 参数修改记录 | 第一版 |
| evaluations | 评估快照 | 第一版 |
| conversations / messages | AI 对话 | 第一版 |
| topic_suggestions / posts | 选题和生成的文案 | 第一版 |
| experiments | 假设验证实验 | 后续 |
| actual_records | 真实经营数据 | 后续 |
| documents | 导出文件（Excel、商业计划书） | 后续 |
| notifications | 提醒（偏差、政策、实验到期） | 后续 |

### sessions 登录会话

| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid | |
| user_id | uuid | |
| token_hash | text | 登录令牌的哈希值（数据库里不存令牌原文） |
| expires_at | timestamptz | 过期时间 |
| last_seen_at | timestamptz | 最近活跃时间 |

### email_tokens 邮件令牌

用于验证邮箱和重置密码。邮件里的链接带有令牌原文，数据库只存哈希值。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid | |
| user_id | uuid | |
| purpose | text | verify_email 验证邮箱 / reset_password 重置密码 |
| token_hash | text | 令牌的哈希值 |
| expires_at | timestamptz | 验证邮箱 24 小时有效，重置密码 1 小时有效 |
| used_at | timestamptz | 使用时间，可空；每个令牌只能用一次 |

### 登录流程

| 场景 | 流程 |
|---|---|
| 注册 | 填写邮箱和密码 → 创建账号（未验证）→ 发送验证邮件 → 用户点击邮件中的链接完成验证 |
| 登录 | 邮箱 + 密码 → 校验通过后创建会话 |
| 忘记密码 | 填写邮箱 → 发送重置链接 → 设置新密码 → 该用户所有会话失效 |
| 修改密码 | 输入旧密码和新密码 → 其他设备上的会话失效 |

### 安全与防刷

- **密码规则**：至少 8 位，拒绝常见弱密码（如 12345678）；不强制要求大小写、符号组合
- **防暴力破解**：同一账号连续失败 5 次锁定 15 分钟；登录、注册、忘记密码接口按 IP 限流（Nginx）
- **防探测**：忘记密码时，无论邮箱是否注册，都提示"如果该邮箱已注册，我们已发送邮件"，避免被用来探测谁注册过
- **防批量注册**（邮箱比手机号更容易批量注册，需要多几道防线）：
  - 未验证邮箱的账号不能使用 AI 功能
  - 每个账号每日有 AI 调用上限
  - 屏蔽常见的一次性临时邮箱域名
  - 注册量出现异常时，再加图形验证码
- **发信**：需要邮件推送服务（阿里云 / 腾讯云），并在域名解析里配置 SPF、DKIM、DMARC 记录，否则邮件容易被归入垃圾箱

### llm_usage 大模型调用计量

| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid | |

## 六、测算参数（profiles.parameters）

### 6.1 参数值的格式

每个参数都是一个对象：

```json
{
  "base": 200,
  "pessimistic": 150,
  "optimistic": 250,
  "source": "user",
  "note": "参考了隔壁同类店外卖月销 4500 单"
}
```

| 字段 | 说明 |
|---|---|
| base | 中性值，必填。可以是数字，也可以是列表（如渠道结构、季节系数） |
| pessimistic / optimistic | 悲观值 / 乐观值，可空；为空时等于 base |
| source | 来源：`user` 用户填写 / `ai_inferred` AI 推断 / `default` 行业默认值 / `experiment` 实验得出 / `actual` 真实数据 |
| note | 说明，如 AI 推断的理由，可空 |

**悲观值指对经营不利的方向**：收入类取低值，成本类取高值。

- 用户明确说出的数字（"房租一万二"），即使是 AI 从对话中提取的，source 也记为 `user`；只有 AI 自己估算的才记为 `ai_inferred`

### 6.3 示例片段

```json
{
  "schema_version": 1,
  "startup": {
    "renovation": { "base": 80000, "pessimistic": 100000, "optimistic": 75000, "source": "user" },
    "deposit_months": { "base": 2, "source": "user" }
  },
  "revenue": {
    "daily_orders": { "base": 200, "pessimistic": 150, "optimistic": 250, "source": "user" },
    "channels": {
      "base": [
        { "name": "堂食", "share": 0.7, "fee_rate": 0 },
        { "name": "外卖", "share": 0.3, "fee_rate": 0.18 }
      ],
      "source": "user"
    }
  },
  "variable_cost": {
    "payment_fee_rate": { "base": 0.006, "source": "default" },
    "tax_rate": { "base": 0.02, "source": "default", "note": "按小规模纳税人估算，待核实" }
  }
}
```

（此例中 f = 0.3 × 0.18 + 0.006 + 0.02 = 0.08，与测算模型中的奶茶店示例一致。）

### 6.4 参数结构升级

- 参数结构带 `schema_version`。以后增减参数时，版本号加 1，并写一个升级函数，把旧版本数据转换成新版本
- 读取档案时如发现旧版本，先升级再使用

  "sensitivity": [
    {
      "key": "revenue.avg_ticket",

## 十二、权限与数据安全

- **只有一个入口读取档案**：代码中写一个统一的函数"取出属于当前用户的档案"（条件：档案 id 匹配、user_id 是当前用户、未删除）。其他所有档案相关的表，都必须先通过这个函数拿到档案，再按 profile_id 查询
- **找不到和无权限统一返回 404**：不让别人通过返回结果判断某个档案是否存在
- **UUID 不能代替权限检查**：它只是让编号难以猜到，权限检查一个都不能少
- **越权测试**：每个接口都写一个测试——用户 B 拿用户 A 的档案编号去访问，必须返回 404
- **管理后台**：第一版不做。需要查数据时用数据库工具直连，只有你本人可以连接
- **删除**：档案软删除后 30 天内可恢复，之后定时任务彻底删除（连同快照、对话、文案）；注销账号同理
- **隐私**：
  - 发送给 DeepSeek 和阿里云百炼的内容，在隐私政策里说明
  - 应用日志里邮箱打码，任何情况下都不记录密码，也不记录对话全文（对话只存在数据库里）
- **备份**：备份文件同样包含敏感数据，加密后再复制到异地

## 十四、已确认的决定

- 一个档案只属于一个用户，第一版不支持合伙人协作
- 档案删除后 30 天内可恢复，之后彻底删除
- 评估快照永久保留
- 登录使用服务器端会话，不用 JWT
- "换个方案试试"用复制档案实现，第一版不做方案分支
