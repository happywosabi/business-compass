# 安全审计记录（2026-11-06）

审计基线：`6db7c3a`，审计开始时工作区干净。覆盖 FastAPI 认证、档案/测算/AI 接口、数据库事务、Vue 渲染、外部请求、Nginx、Compose 和依赖。

发现 **6 项应用代码问题：2 项高危、4 项中危**，另有 **1 项具有高危影响的部署配置风险**。风险等级结合当前默认单进程部署判断，不代表经过认证的 CVSS 评分。本次仅提交审计记录，未修改业务实现。

## 验证方法与边界

- 在独立、仅绑定本机端口的 PostgreSQL 临时容器中创建专用测试库；未写入项目现有业务数据库。
- 认证、邮件和热点问题通过真实 FastAPI ASGI 请求及 PostgreSQL 验证；邮件使用 `MemoryMailSender`，热点使用模拟搜索和模型，没有发送真实邮件或调用收费 AI。
- 登录并发问题使用测试屏障控制密码校验的执行顺序，验证可发生的事务交错；这不是对公网入口实测成功率的证明。Nginx 每 IP 限流仍会约束请求频率，但不会修复这些事务竞争。
- 果园性能测试在独立本地进程和 ASGI 应用中进行，没有向正在使用的服务发送重负载请求。
- 对现有容器仅做配置、端口、HTTP 响应头和健康状态的只读核查；没有审计外部 HTTPS 代理、云防火墙或真实公网域名。

## 1. 高危：重置密码后，在途旧密码登录仍可签发有效会话

位置：`backend/app/auth/service.py:217`、`:224`、`:244`、`:318`、`:326`；会话验证位于同文件 `:260`。

登录先读取用户和密码哈希，再在线程中执行 Argon2 校验，之后直接插入会话。读取、密码校验和会话签发没有与密码重置进行互斥，也没有在签发前重新核对密码版本。重置流程删除的是当时可见的会话；`authenticate()` 也没有利用 `password_changed_at` 判断会话签发依据是否过期。

可发生以下顺序：

1. 攻击者使用已泄露的旧密码登录，完成旧哈希校验，尚未提交会话。
2. 用户完成密码重置，服务修改密码并删除当时所有会话。
3. 攻击者先前的登录继续执行并提交新会话。

**实测：**重置密码返回 200；恢复在途旧密码登录后返回 200；该新会话访问 `/api/auth/me` 仍返回 200。用户通过重置密码回收访问权的操作因此失效。正常修改密码与登录之间也缺少同一用户级别的协调。

**修复建议：**让登录签发、改密和重置采用统一的用户级事务保护。可在密码校验后锁定用户行并重新核对校验时的哈希/密码版本，再签发绑定该版本的会话；改密和重置递增版本并吊销相关会话。只在认证时比较会话创建时间不够，因为竞争中的会话可能在重置之后才创建。

## 2. 高危：低权限果园测算可长时间阻塞整个 API 事件循环

位置：`backend/app/engine/orchard.py:363`、`:370`、`:375`、`:381`；`backend/app/evaluations/service.py:139`、`:150`；`backend/app/evaluations/router.py:64`；`backend/Dockerfile:33`。

敏感性分析对每个具有悲观/乐观范围的嵌套数值都深复制全部参数、重新执行完整模型校验、重新计算全部品种。计算量随着嵌套条目数接近平方增长。50 个品种、每品种 20 个等级、每等级 2 个渠道的现有限制仍允许大量重复计算。

这些同步计算直接运行在 `async def` 接口内，没有计算预算、后台进程隔离或测算频率限制。测算只要求 `CurrentUser`，不要求验证邮箱。当前 Docker 启动命令也未配置多个 Uvicorn worker。

**实测：**

| 合法输入 | 输入 JSON 大小 | 结果 |
| --- | ---: | --- |
| 5 品种，每品种 1 等级，多个数值提供范围 | 4,849 字节 | 纯计算约 0.025 秒 |
| 10 品种，每品种 5 等级 | 27,369 字节 | 纯计算约 0.753 秒 |
| 25 品种，每品种 10 等级 | 124,194 字节 | 通过校验，运行 12 秒仍未结束，测试进程主动终止 |

另以未验证邮箱账号通过 API 创建约 27 KB 的合法果园档案并调用 `/what-if`，请求返回 200，同时事件循环定时器出现约 **1.17–1.31 秒**的停顿。`what-if` 会计算原方案和修改方案，两次执行敏感性分析。上述输入均低于 Nginx 的 1 MB 请求上限。

**影响：**少量普通账号请求就可能让同进程的其他登录、健康检查和业务请求延迟；重复请求会进一步占用服务。

**修复建议：**限制每次敏感性分析允许的范围数量/总复杂度，避免对每个数值重复全量校验；将计算放入具有并发和执行时限限制的独立进程或任务队列，给用户和 IP 设置测算预算。单纯添加 `asyncio.timeout()` 不能中断正在事件循环中执行的同步 CPU 计算。

## 3. 中危：登录失败次数存在丢失更新，绕过“五次失败锁定”

位置：`backend/app/auth/service.py:217`、`:224`、`:225`。

失败计数通过 Python 的 `user.failed_login_count += 1` 更新，没有行锁或原子递增。多个请求可读取相同的计数，随后将相同的新值依次覆盖回数据库。

**实测：**8 个并发错误密码请求全部返回 401，数据库 `failed_login_count` 最终为 1，`locked_until` 为空。顺序请求第五次锁定的现有测试无法覆盖这一情况。

**影响：**提高单账号可尝试的密码数量，削弱账号锁定防护；外围每 IP 限流仍存在，不能把此问题表述为完全无限制的暴力破解。

**修复建议：**用数据库原子更新递增并根据更新结果决定锁定，或在同一用户行锁下完成检查及更新；与第 1 项使用一致的事务锁顺序。增加同时发起多个错误密码请求的测试。

## 4. 中危：成功改密不会撤销此前签发的密码重置令牌

位置：`backend/app/auth/service.py:330`、`:340`、`:343`；重置令牌查询位于 `:118`。

`change_password()` 更新密码并删除其他设备会话，但没有使已有 `reset_password` 令牌失效。令牌消费时仅检查有效期和 `used_at`，不检查令牌是否早于最近一次密码变更。

**实测：**先申请重置邮件，再以原密码正常改密，两个操作均成功；随后使用改密之前邮件中的令牌再次重置密码，仍返回 200。

**影响及前提：**攻击者必须已经取得一个尚未使用的重置令牌。用户通过正常改密处理泄露事件后，该旧令牌在原有效期内仍可再次接管账号。仅知道邮箱无法利用此问题。

**修复建议：**在改密/重置的同一事务中撤销该用户全部未使用的重置令牌，并在令牌消费时校验密码版本或签发时间。与令牌签发采用一致的用户锁，避免新旧请求交错留下额外有效令牌。

## 5. 中危：并发请求绕过邮件频率限制，并留下多个有效重置令牌

位置：`backend/app/auth/service.py:78`、`:85`、`:88`、`:98`、`:105`。

邮件发送先查询最近发送时间和当日数量，再使旧令牌失效并插入新令牌。这些操作没有用户/用途级互斥或防止竞争的数据库约束。多个请求可同时通过频率和数量检查，旧令牌失效语句也无法保证覆盖并发事务中尚未提交的新令牌。

**实测：**将每日限额设置为 2，向同一专用测试账号同时发出 8 次忘记密码请求，短时间内产生了 **5 封邮件和 4 个同时有效的重置令牌**。具体数量随调度变化，但已同时突破 60 秒间隔、每日限额，以及“只保留最新令牌”的约束。

**影响：**邮件骚扰与发送成本增加；多个令牌延长凭据管理和事件处置中的暴露面。

**修复建议：**在用户/用途锁保护下完成检查、旧令牌撤销和新令牌写入；需要时使用受锁保护的发送计数/预约记录。邮件失败和重试也应复用同一发送预约。

## 6. 中危：热点刷新可绕过 AI 日配额和调用用量记录

位置：`backend/app/content/router.py:63`、`:73`；`backend/app/content/hot.py:138`、`:166`；配额入口是 `backend/app/llm/runs.py:18`。

热点刷新只验证邮箱和档案归属，随后直接调用热点采集。采集会调用 LLM 筛选，并可进一步调用 Embedding，未经过 `reserve()` 的每日配额/并发控制，也没有创建 `AIRun` 或保存该次调用的 token 用量。

**实测：**已验证账号的 `daily_ai_quota=0`，刷新接口仍返回 200，模拟模型被调用一次，该用户的 `ai_runs` 记录数保持为 0。

**影响及限制：**普通用户可以触发未记入账号额度的付费工作。现有全局两分钟冷却和 PostgreSQL advisory lock 会限制成功刷新频率，所以不是无限并发调用；但用户仍可将后台默认两小时一次的工作推进到更高频率。若此工作本来定义为系统公共预算，应明确采用系统预算控制，不能依赖个人 AI 配额限制它。

**修复建议：**将手动刷新纳入可审计的公共预算、每日上限、执行总时限和调用记录，或限定为后台任务/有权限的管理操作；同时约束异常期间的重试成本。

## 7. 部署风险（公网沿用时高危）：HTTP 与非 Secure 会话 Cookie

位置：`compose.yaml:68`、`deploy/nginx/default.conf:12`、`.env.example:8`、`:22`、`backend/app/main.py:33`。

默认 Compose 把 HTTP 端口发布到所有主机地址，仓库 Nginx 只监听 80，无 TLS。模板允许非 Secure Cookie。生产模式遇到非 HTTPS 基址和非 Secure Cookie 只打印警告，不拒绝启动。

**当前只读核查：**Nginx 容器发布在 `0.0.0.0:8080` 和 `[::]:8080`；API 配置为 `development`、`session_cookie_secure=False`、邮件基址不使用 HTTPS。此处没有输出真实密钥，也不能据此推断公网防火墙开放或不存在外部 TLS 代理。

**影响及前提：**若公网部署沿用该入口或能绕过前置 HTTPS 代理访问 HTTP，登录密码、会话及重置流程可能遭网络窃听/篡改。外部已有 TLS 并不自动消除公开 HTTP 旁路。

**修复建议：**对外强制 HTTPS；TLS 在前置代理终止时只向受控本机/内网地址发布应用 HTTP 端口；生产环境启用 Secure Cookie、HTTPS 邮件链接及适当的 HSTS，并将关键错误配置改为启动失败。纯本机开发保留独立配置。
